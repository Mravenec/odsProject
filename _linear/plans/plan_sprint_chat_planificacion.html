Chat de revisión en planificación
gestor ⇄ evaluador/admin · transición con aprobación

Mientras un proyecto está en planificacion, habilitar un chat por proyecto entre el gestor (dueño) y cualquier administrador o evaluador. Admin/evaluador pueden editar el proyecto y señalar errores (p. ej. una fórmula mal); los mensajes se editan estilo WhatsApp (≤30 min). El gestor solicita salir de planificación (a activo o cancelado) y un admin/evaluador aprueba; al salir, el chat se congela y se bloquea la edición por admin/evaluador.

Objetivo
Qué se busca resolver
Problema actualSolución propuesta
En planificacion no hay canal de ida y vuelta entre el gestor y los revisores; si hay un error (fórmula, meta, ODS mal vinculado) no hay dónde discutirlo dentro del proyecto.Chat por proyecto (tabla proyecto_chat_mensajes) visible para gestor dueño + admin + evaluador, activo solo en planificacion.
Cualquier revisor que entre no sabe por dónde iba la conversación previa.Hilo persistente y ordenado por fecha: cualquier admin o evaluador continúa donde quedó.
Un mensaje enviado por error no se puede corregir.Edición/borrado del propio mensaje dentro de 30 min (estilo WhatsApp); después queda bloqueado. Marca “editado”.
El paso de planificacion a activo no tiene control ni registro de quién lo autorizó.El gestor solicita la transición (activo o cancelado); admin/evaluador aprueba o rechaza. Queda sellado quién y cuándo (tabla proyecto_transicion_solicitud).
No está claro hasta cuándo admin/evaluador pueden tocar el proyecto.Editan el proyecto solo en planificacion. Al aprobarse la salida, se congela el chat y se bloquea su edición; desde activo solo cabe cancelar por fuerza mayor.
Reglas de negocio
Comportamiento aprobado (decisiones confirmadas)
ReglaDetalle
Alcance del chatSolo cuando proyectos.estado = 'planificacion'. En cualquier otro estado el hilo queda en solo lectura.
ParticipantesGestor dueño del proyecto + cualquier usuario con rol admin o evaluador (ids de rol 1 y 4).
Ventana de ediciónEl autor edita/borra su propio mensaje hasta 30 min tras created_at. Validación en la capa de servicio (NOW() vs created_at), no en SQL.
Edición del proyectoEn planificacion: gestor dueño + admin + evaluador. Fuera de planificacion: bloqueada para admin/evaluador.
Salir de planificaciónGestor crea solicitud (destino activo | cancelado, con motivo). Una sola solicitud pendiente por proyecto.
ResoluciónAdmin/evaluador aprueba → estado = destino + chat congelado; o rechaza (con nota) → sigue en planificacion, el chat continúa.
Fuerza mayorDesde activo, admin/evaluador pueden pasar a cancelado (excepción, con motivo). El resto del ciclo (activo → en_revision → completado, rechazo, etc.) no cambia.
Máquina de estadosEl ENUM('planificacion','activo','en_revision','completado','cancelado') no se modifica. La “solicitud + aprobación” se modela en tabla aparte para no romper el flujo existente ni JOOQ.
# Transición de salida de planificación (nuevo control; el ENUM no cambia) planificacion ──solicita(gestor)──> [solicitud: pendiente] ──aprueba(admin|evaluador)──> activo | cancelado └─rechaza(admin|evaluador)──> planificacion (chat sigue) activo ──fuerza mayor (admin|evaluador)──> cancelado

Modelo de datos
Tablas nuevas en ods_master (sin tocar proyectos.estado)
-- proyecto_chat_mensajes — hilo del proyecto en planificación CREATE TABLE proyecto_chat_mensajes ( id INT AUTO_INCREMENT PRIMARY KEY, proyecto_id INT NOT NULL, autor_id INT NOT NULL, cuerpo TEXT NOT NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, edited_at TIMESTAMP NULL, -- marca "editado" edit_count INT DEFAULT 0, eliminado BOOLEAN DEFAULT FALSE, -- borrado lógico (≤30 min) eliminado_at TIMESTAMP NULL, FOREIGN KEY (proyecto_id) REFERENCES proyectos(id) ON DELETE CASCADE, FOREIGN KEY (autor_id) REFERENCES ods_login.usuarios(id), INDEX idx_chat_proyecto (proyecto_id, created_at) ) ENGINE=InnoDB; -- proyecto_transicion_solicitud — gestor solicita / admin|evaluador resuelve CREATE TABLE proyecto_transicion_solicitud ( id INT AUTO_INCREMENT PRIMARY KEY, proyecto_id INT NOT NULL, solicitado_por INT NOT NULL, -- gestor dueño estado_destino ENUM('activo','cancelado') NOT NULL, motivo VARCHAR(1000) NULL, estado_solicitud ENUM('pendiente','aprobada','rechazada') DEFAULT 'pendiente', resuelto_por INT NULL, -- admin/evaluador resuelto_en TIMESTAMP NULL, nota_resolucion VARCHAR(1000) NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (proyecto_id) REFERENCES proyectos(id) ON DELETE CASCADE, FOREIGN KEY (solicitado_por) REFERENCES ods_login.usuarios(id), FOREIGN KEY (resuelto_por) REFERENCES ods_login.usuarios(id), INDEX idx_sol_proyecto (proyecto_id), INDEX idx_sol_estado (estado_solicitud) ) ENGINE=InnoDB;

Regla “una sola solicitud pendiente por proyecto” y ventana de 30 min se aplican en la capa de servicio Java (mismo criterio que la unicidad del ODS primario en MasterProjectRepository.linkOds, ya documentado en el schema actual).

Antes / Después
Experiencia en la fase de planificación

Antes

Sin canal dentro del proyecto. El revisor avisa de un error por fuera (correo, verbal). El gestor cambia planificacion → activo sin registro de quién lo autorizó. No se sabe hasta cuándo admin/evaluador pueden corregir.

Después

Chat por proyecto: el revisor señala el error y lo corrige en el momento. Mensajes editables 30 min. El gestor solicita salir; admin/evaluador aprueba/rechaza con sello de quién y cuándo. Al aprobar, chat congelado y edición bloqueada.
